## Conditional three-LP diagnostic

The new `scripts/round91_handling_rounding_diagnostic.py` is a small separate Gurobi Python driver, using the existing local `build/research/round88-ot/venv/Scripts/python.exe` after its version/environment is rechecked. Its only launch form is:

```powershell
& 'build/research/round88-ot/venv/Scripts/python.exe' scripts/round91_handling_rounding_diagnostic.py supervise --manifest <verified-export-dir>/export_manifest.json --admission <root-signed-admission.json> --out <new-diagnostic-dir>
```

The supervisor starts one **300-second shared diagnostic deadline** before manifest/source preflight and passes the remaining absolute monotonic deadline to its child. The child imports Gurobi only after that deadline starts, then sequentially reads and relaxes the same SHA-pinned full canonical LP independently for A, B and C, retaining all original rows, bounds, G interval and verifier-F cutoff. Each arm maximizes `Σ_{i=1}^5 state_i_1`; A adds nothing, B only the two `Σ_i p_0_i≤2` and `Σ_i p_1_i≤2` rows, C only `Σ_i state_i_1≤4`. The remaining whole-item time is forwarded to each Gurobi `TimeLimit`, with Threads 1, Seed 0 and Presolve Auto; there are no arm quotas or retries. Timeout or a nonoptimal/numerically uncertified arm stops the sequence and is `unknown`, not an objective comparison. The supervisor's 300 seconds start after its own interpreter/standard-library startup; its receipt therefore names `supervisor_body_wall_seconds`. **Actual A/B/C execution is conditional on a separate outer process-tree watchdog and launch-to-exit receipt enforcing the same 300-second research ceiling**, including Python startup, parent preflight and final receipt writes. Any outer overrun is `unknown` even if the inner script reports completion. The script alone does not provide this required hard parent-process cap; root must bind the watchdog command and its receipt in the later execution admission.

The admission/preflight checks actual input/LP/source hashes, full canonical scope, objective, G domain, cutoff, exact `p∈[0,2]`/`d=0` domains and types, and the one-hot, `Y` reconstruction and inventory-balance rows for all five stations. These identity checks make the fixed fixture's `B⇒C` relation inspectable on the actual exported model. For each arm, the driver saves full primal, every original/added row residual, every variable bound residual, actual parameters/status, original F/G/P at the relaxed point, per-vehicle pickup sums, five `state_i_1`, LP matrix signature, optimization Work/iterations/runtime, read/relax/serialize cost and peak working set. Supervisor saves stdout/stderr, complete outer cost and failure/timeout identity. A numerical optimum comparison is permitted only when all three arms finish `OPTIMAL`, original/additional row and bound residuals pass the documented solver-tolerance-plus-floating-error test, and all source/matrix identities stay fixed. A>4 with B,C≤4 would expose a **per-vehicle handling-rounding gap already dominated by B**, not a novel B3 cut. A≤4 means only this fixed five-station inequality is already implied on this root LP. No result here qualifies a production cut, broad convex-hull claim, or MIP speed improvement.

The status strings `certified_optimal_primal` and `all_three_certified` mean **Gurobi reports numerical OPTIMAL and every saved original/added row and variable-bound residual passes its recorded tolerance-plus-roundoff allowance**. They are not rational primal-dual certificates or a strict mathematical LP proof. A near-4 result requires its numerical margin to be reported, not a categorical inequality claim beyond that precision.
